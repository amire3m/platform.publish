# Workflow Core and RBAC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the normalized workflow data model, deterministic state engine, progress/next-action queries, RBAC, and base APIs for programs, deliverables, publications, and templates.

**Architecture:** `workflow_*` records are PostgreSQL-authoritative and isolated behind a port-based repository. Pure domain modules own transitions and derived progress; route handlers only authenticate, validate, and call a transaction-aware service. Existing `content` and Telegram-backed records are not changed in this phase.

**Tech Stack:** Next.js 16 App Router, TypeScript 5.9, Drizzle ORM 0.45, PostgreSQL, Zod 4, Vitest 4.

**Spec:** `docs/superpowers/specs/2026-08-22-content-workflow-design.md`

## Global Constraints

- Use TDD: observe each focused test fail before writing production code.
- `workflow_*` data is PostgreSQL-authoritative; do not call TGDB for these entities.
- Do not modify legacy `content` or `platformTargets` in this phase.
- IDs remain text IDs generated by `generateEntityId`; add explicit workflow prefixes.
- Every mutation accepts `expectedVersion`; stale writes return domain code `VERSION_CONFLICT` and API status 409.
- A workflow-only mutation writes entity changes and `workflow_events` in one transaction.
- Hard delete is forbidden after a program is persisted.
- API errors use `jsonError`; successful responses use `jsonOk`.
