# طراحی آمار واقعی یوتیوب

تاریخ: 2026-08-21

## هدف

تبدیل داشبورد و بخش آمار فعلی از نمایش داده‌های placeholder به یک سامانه واقعی برای جمع‌آوری، نگهداری و گزارش آمار کانال‌ها و ویدیوهای یوتیوب. نسخه اول باید داشبورد مدیریتی، جزئیات عملکرد ویدیوها، بازه‌های 7/30/90 روزه، خروجی CSV، همگام‌سازی روزانه و همگام‌سازی دستی را پوشش دهد.

این فاز به Meta یا Facebook وابسته نیست. ساختار داده طوری طراحی می‌شود که بعداً آمار Instagram نیز بدون ایجاد مسیر گزارش‌گیری جداگانه به آن افزوده شود.

## دامنه

### در دامنه

- آمار واقعی کانال و ویدیو از YouTube Data API v3 و YouTube Analytics API.
- snapshot روزانه در سطح حساب و محتوا.
- همگام‌سازی روزانه و دستی با گزارش نتیجه هر کانال.
- داشبورد مجموع و روند برای بازه‌های 7، 30 و 90 روز.
- جدول و جزئیات بهترین ویدیوها.
- فیلتر کانال، بازه زمانی و سطح حساب/محتوا.
- خروجی CSV منطبق با فیلتر فعال.
- کنترل دسترسی بر اساس permission و `allowedAccountIds`.
- تست سرویس جمع‌آوری، محاسبات، API، دسترسی و CSV.

### خارج از دامنه

- Instagram Insights تا زمان رفع دسترسی Meta.
- پیش‌بینی رشد، پیشنهاد محتوا و تحلیل هوش مصنوعی.
- داده لحظه‌ای؛ دقت مورد انتظار روزانه است.
- تغییر چرخه انتشار محتوا یا طراحی مجدد کل پنل.

## منابع داده و معنای شاخص‌ها

دو API گوگل استفاده می‌شوند:

1. YouTube Data API برای مشخصات کانال/ویدیو و شمارنده‌های عمومی مانند `subscriberCount`، `viewCount` و اطلاعات عنوان و thumbnail.
2. YouTube Analytics API برای شاخص‌های بازه‌ای مانند `views`، `estimatedMinutesWatched`، `averageViewDuration`، `likes`، `comments`، `shares`، `subscribersGained` و `subscribersLost`.

مجوز `yt-analytics.readonly` هم‌اکنون در `YOUTUBE_OAUTH_SCOPES` وجود دارد. کانال قدیمی که این scope را در توکن خود ندارد باید با پیام مشخص دوباره متصل شود.

تعریف شاخص‌ها:

- مشترک فعلی: شمارنده فعلی کانال از Data API، نه جمع snapshotها.
- بازدید، تعامل و زمان تماشا: مقدار دوره‌ای Analytics API، قابل جمع در بازه انتخابی.
- رشد مشترک: `subscribersGained - subscribersLost` در بازه.
- نرخ تعامل: `(likes + comments + shares) / views * 100`؛ در صورت صفر بودن بازدید، صفر است.
- مقایسه دوره: بازه انتخابی با بازه بلافاصله قبل از آن با طول برابر مقایسه می‌شود.
- تاریخ روزانه: مرز گزارش با timezone کانال در صورت دسترسی و در غیر این صورت `Asia/Tehran` محاسبه، ولی timestamp در دیتابیس به UTC ذخیره می‌شود.

## مدل داده

جدول عمومی `analytics_snapshots` حفظ و برای دو سطح توسعه می‌یابد:

- `scopeType`: مقدار `account` یا `content`.
- `scopeId`: برای حساب، شناسه داخلی `social_accounts.id`؛ برای محتوا، شناسه ویدیوی خارجی یوتیوب.
- `contentTitle`، `thumbnailUrl` و `publishedAt`: metadata لازم برای گزارش ویدیو، nullable برای سطح حساب.
- `subscribersGained` و `subscribersLost`: برای محاسبه رشد واقعی.
- شاخص‌های موجود مانند views، likes، comments، shares، watchTime و averageViewDuration استفاده می‌شوند.
- `rawMetrics` فقط پاسخ تکمیلی یا شاخص‌هایی را نگه می‌دارد که هنوز ستون تثبیت‌شده ندارند؛ منبع اصلی شاخص‌های نمایش‌داده‌شده ستون‌های typed هستند.

یک unique index روی `(platform, accountId, scopeType, scopeId, dateUtc)` مانع snapshot تکراری می‌شود. `dateUtc` برای snapshot روزانه به ابتدای روز گزارش normalize می‌شود. رکوردهای قدیمی با `scopeType=account` و `scopeId=accountId` مهاجرت داده می‌شوند.

ویدیوهای منتشرشده توسط همین پلتفرم از طریق external ID هدف انتشار به محتوای داخلی قابل تطبیق‌اند. ویدیوهای دیگر کانال نیز با external ID نمایش داده می‌شوند و برای حضور در گزارش نیازی به رکورد داخلی `content` ندارند.

وضعیت هر حساب در `social_accounts.lastSyncAt`، `social_accounts.lastError`، کد پایدار `analyticsLastErrorCode` و زمان محافظه‌کارانه `analyticsNextAttemptAt` ثبت می‌شود. cursor مستقل `analyticsSyncedThrough` انتهای انحصاری آخرین بازه موفق را حتی برای گزارش خالی نگه می‌دارد. `lastSyncAt` و cursor فقط در commit موفق و fence‌شده همان حساب تغییر می‌کنند.

## معماری سرویس همگام‌سازی

یک سرویس مستقل در لایه `lib` مسئول تمام همگام‌سازی‌ها خواهد بود. API دستی و Cron فقط این سرویس را فراخوانی می‌کنند.

جریان هر حساب:

1. اطمینان از `platform=youtube`، فعال و `connectionStatus=connected`.
2. خواندن و رمزگشایی credential فقط در سمت سرور.
3. ساخت OAuth client و refresh خودکار access token توسط refresh token موجود.
4. دریافت مشخصات و شمارنده فعلی کانال.
5. تعیین بازه افزایشی: از روز بعد آخرین snapshot موفق تا روز کامل گذشته. در اولین اجرا، 90 روز گذشته backfill می‌شود.
6. دریافت گزارش روزانه سطح کانال.
7. دریافت گزارش روزانه سطح ویدیو با pagination تا پایان نتایج؛ metadata ویدیوها در batchهای حداکثر 50تایی از Data API گرفته می‌شود.
8. تطبیق `channelId` تمام ردیف‌های حساب/محتوا با external ID حساب و سپس تبدیل پاسخ API به مدل داخلی و upsert تراکنشی snapshotها همراه cursor.
9. ثبت `lastSyncAt` یا خطای secret-safe در همان حساب.
10. برگرداندن نتیجه ساختاریافته شامل تعداد روزها، ویدیوها، snapshotها و خطا.

همگام‌سازی چند حساب با pool محدود (پیش‌فرض سه حساب) مستقل است. شکست یک کانال اجرای کانال‌های بعدی را متوقف نمی‌کند؛ پس از مشاهده پایان سهمیه، حساب جدیدی شروع نمی‌شود. اجرای هم‌زمان برای یک حساب با lease و fence نهایی تراکنش جلوگیری می‌شود تا worker منقضی نتواند snapshot، cursor یا وضعیت worker جدید را بازنویسی کند.

## زمان‌بندی و سهمیه API

- Cron روزانه یک بار بعد از کامل‌شدن روز قبلی اجرا می‌شود.
- همگام‌سازی دستی از UI قابل اجرا است و همان سرویس را استفاده می‌کند.
- sync افزایشی فقط روزهای ازدست‌رفته را درخواست می‌کند.
- اولین sync حداکثر 90 روز backfill دارد تا هزینه و زمان قابل کنترل بماند.
- ویدیوها و metadata به‌صورت batch و paginated دریافت می‌شوند؛ هیچ محدودیت پنهانی مانند «فقط 200 ویدیوی برتر» اعمال نمی‌شود.
- retry فقط برای خطاهای موقت، `429` و `5xx` با حداکثر سه تلاش و backoff افزایشی انجام می‌شود.
- خطاهای `401/403` retry نمی‌شوند و به‌عنوان نیازمند اتصال مجدد یا فعال‌سازی API ثبت می‌شوند.

## API داخلی

### `POST /api/analytics/sync`

- permission لازم: `view_analytics` برای sync حساب‌های مجاز کاربر؛ اجرای همه حساب‌ها فقط برای ادمین دارای `manage_accounts`.
- ورودی اختیاری: `accountId`.
- خروجی: نتیجه مستقل هر حساب شامل status، snapshot count، date range و خطای قابل نمایش.
- پاسخ موفق HTTP می‌تواند شامل شکست جزئی باشد؛ وضعیت هر حساب در payload صریح است.

### `GET /api/analytics/overview`

- پارامترها: `range=7|30|90` و `accountId` اختیاری.
- خروجی: totals، تغییر نسبت به دوره قبل، series روزانه، top videos، freshness و sync status.
- محاسبات تنها روی حساب‌های مجاز کاربر انجام می‌شوند.

### `GET /api/analytics/content/:externalId`

- پارامترهای بازه مانند overview.
- خروجی: metadata ویدیو، totals، series، مقایسه با دوره قبل و میانگین کانال.
- دسترسی از طریق account مالک ویدیو کنترل می‌شود.

### `GET /api/analytics/export`

- همان فیلترهای UI را می‌پذیرد: range، accountId و scope.
- CSV با UTF-8 BOM، header فارسی پایدار و تاریخ قابل خواندن تولید می‌شود.
- داده خروجی باید با داده نمایش‌داده‌شده در همان فیلتر برابر باشد.

## رابط کاربری

صفحه Analytics فعلی توسعه می‌یابد و زبان فارسی، RTL و الگوی بصری موجود حفظ می‌شود.

اجزای اصلی:

- فیلتر کانال و انتخاب بازه 7/30/90 روز.
- کارت‌های بازدید، مشترک فعلی، رشد مشترک، زمان تماشا و نرخ تعامل؛ هر کارت تغییر نسبت به دوره قبل را نشان می‌دهد.
- نمودار روند روزانه با امکان انتخاب شاخص.
- جدول بهترین ویدیوها با عنوان، thumbnail، کانال، تاریخ انتشار، بازدید، زمان تماشا، نرخ تعامل و تغییر دوره‌ای.
- صفحه یا پنل جزئیات ویدیو با روند و مقایسه با میانگین کانال.
- دکمه «همگام‌سازی اکنون» با حالت loading و نتیجه هر کانال.
- دکمه CSV که فیلتر جاری را حفظ می‌کند.
- نمایش زمان آخرین sync و وضعیت fresh/stale/error.

در موبایل، کارت‌ها افقی قابل پیمایش می‌شوند، نمودار عرض کامل دارد و جدول به لیست خلاصه ویدیوها تبدیل می‌شود. حالت‌های empty، loading، stale، partial failure و reconnect-required باید متن عملی و مشخص داشته باشند.

## کنترل دسترسی

- تمام endpointهای آمار به `view_analytics` نیاز دارند.
- queryها پیش از aggregate شدن با `allowedAccountIds` محدود می‌شوند؛ فیلتر صرفاً در UI کافی نیست.
- کاربر نمی‌تواند با واردکردن دستی `accountId` یا external video ID داده کانال غیرمجاز را ببیند.
- credential و پاسخ خام حاوی token هرگز به مرورگر، audit log یا متن خطا وارد نمی‌شوند.
- اجرای sync همه حساب‌ها نیازمند `manage_accounts` است؛ کاربران محدود فقط حساب‌های مجاز خود را sync می‌کنند.

## مدیریت خطا

- خطای هر حساب مستقل ذخیره و نمایش داده می‌شود.
- خطای scope یا token پیام اتصال مجدد یوتیوب می‌دهد.
- فعال‌نبودن YouTube Analytics API پیام پیکربندی پروژه Google می‌دهد.
- سهمیه تمام‌شده زمان تلاش بعدی را مشخص می‌کند و داده قبلی همچنان قابل مشاهده می‌ماند.
- endpoint کرون فقط POST است، در نبود `CRON_SECRET` با 503 fail closed می‌شود و job انتشار و آمار را مستقل اجرا می‌کند.
- CSV سلول‌های متنی با پیشوند فرمول را بدون تغییر serialization اعداد خنثی می‌کند.
- در شکست جزئی، snapshotهای کامل‌شده حفظ می‌شوند و freshness حساب شکست‌خورده تغییر نمی‌کند.
- UI داده قدیمی را با برچسب stale نمایش می‌دهد و آن را با صفر جایگزین نمی‌کند.

## آزمون‌ها

برای پروژه test runner و script استاندارد اضافه می‌شود. تست‌ها شامل موارد زیر هستند:

- تبدیل پاسخ Data API و Analytics API به مدل snapshot.
- normalization روز و محاسبات timezone.
- upsert مجدد بدون ایجاد رکورد تکراری.
- sync افزایشی و backfill اولیه 90روزه.
- pagination و batch metadata بدون حذف ویدیوهای کم‌بازدید.
- محاسبه totals، نرخ تعامل و مقایسه دوره قبلی برای 7/30/90 روز.
- رفتار صفر بازدید و داده ناقص.
- ادامه sync سایر کانال‌ها پس از شکست یک کانال.
- طبقه‌بندی خطاهای retryable و reconnect-required.
- محدودسازی `allowedAccountIds` در overview، detail، export و sync.
- برابر بودن محتوای CSV با فیلتر و داده API.
- تست API با پاسخ‌های mock گوگل؛ هیچ تستی به API واقعی یا credential تولید وابسته نیست.

## مهاجرت و عرضه

1. افزودن ستون‌ها و unique index با migration قابل rollback.
2. backfill رکوردهای قدیمی به scope حساب.
3. استقرار سرویس sync و endpointها بدون فعال‌کردن Cron.
4. اجرای sync دستی روی یک کانال تست و مقایسه با YouTube Studio.
5. فعال‌کردن UI جدید و CSV.
6. فعال‌کردن Cron روزانه پس از تأیید سهمیه و صحت داده.

داده قدیمی حذف نمی‌شود. اگر migration یا sync اولیه شکست بخورد، داشبورد موجود باید داده قبلی را با وضعیت stale نمایش دهد.

## معیارهای پذیرش

- ادمین می‌تواند یک کانال متصل را sync کند و نتیجه واقعی همان کانال را ببیند.
- اجرای تکراری sync برای همان روز snapshot تکراری تولید نمی‌کند.
- داشبورد بازه‌های 7/30/90 روز را با مقایسه دوره قبل نشان می‌دهد.
- بهترین ویدیوها و جزئیات هر ویدیو از داده واقعی ساخته می‌شوند.
- CSV با فیلتر UI منطبق است.
- Cron روزانه همان منطق sync دستی را اجرا می‌کند.
- شکست یک کانال مانع sync سایر کانال‌ها نمی‌شود.
- کاربر محدود هیچ داده‌ای از کانال خارج از `allowedAccountIds` دریافت نمی‌کند.
- token یا secret در API response و log ظاهر نمی‌شود.
- تست‌های واحد و integration مربوط به این قابلیت پاس می‌شوند.
